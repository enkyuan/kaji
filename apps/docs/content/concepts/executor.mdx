---
title: Execution
description: Follow the one governed path from request to recorded result.
---

Create one executor with stable application configuration:

```ts
const kaji = createKaji({
  store,
  approve,
  timeoutMs: 15_000,
});
```

Then use `kaji.execute()` for every governed capability call.

## Request

```ts
export type ExecutionRequest = {
  readonly input: unknown;
  readonly principalId: string;
  readonly idempotencyKey: string;
  readonly signal?: AbortSignal;
};
```

The caller supplies all request fields. `principalId` and `idempotencyKey` must be non-empty strings.

Invalid metadata or invalid capability input rejects before Kaji creates a store claim. Kaji does not call authorization, approval, or capability execution in this case.

## Order

For a new valid claim, Kaji runs these steps:

1. Validate capability input.
2. Claim the execution identity.
3. Check authorization.
4. Request approval when required.
5. Call the capability `execute` function.
6. Record the result.

An existing identical claim returns its stored or pending result. Kaji does not call the capability again.

A claim with the same identity and different validated input returns `status: "failed"` as an idempotency conflict.

## Context

Capability execution receives this context:

```ts
export type ExecutionContext = {
  readonly principalId: string;
  readonly idempotencyKey: string;
  readonly signal: AbortSignal;
};
```

The signal combines the caller signal with the optional Kaji timeout. `timeoutMs` aborts this signal but does not forcibly terminate `execute()`.

Kaji awaits `execute()` until it settles. The capability or downstream API must observe the signal for cancellation to interrupt work.

Pass the idempotency key to an external provider when the provider supports idempotency. Kaji cannot make an external provider idempotent by itself.

## Return and rejection behavior

After Kaji establishes an execution claim, expected outcomes resolve as `ExecutionResult` values.

Kaji can reject before the claim exists. Examples include invalid request metadata, invalid capability input, and a store claim failure.

After capability execution begins, a normal thrown error resolves as `status: "unknown"`. Throw `knownFailure(cause)` only when no side effect committed.

Read [Outcomes](/docs/concepts/outcomes) for every result status.

## Store settlement

Kaji records each terminal result through `store.record()`.

When this record call fails, Kaji returns `status: "unknown"`. The returned status no longer confirms that the intended terminal result was stored.

A repeated request depends on store behavior. Production safety therefore depends on the configured `ExecutionStore`.
