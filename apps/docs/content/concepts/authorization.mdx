---
title: Authorization
description: Keep application policy inside the Kaji execution boundary.
---

Every capability must define `authorize`.

```ts
authorize: ({ principalId, input }) => canRefund(principalId, input);
```

## Inputs

Kaji calls `authorize` with:

- the caller-supplied `principalId`
- the validated capability input

Kaji does not authenticate the caller or infer `principalId`. The application adapter must establish identity before it calls `kaji.execute()`.

## Decision behavior

`authorize` can return `true`, `false`, or a promise of either value.

A `true` result lets Kaji continue to approval or execution.

A `false` result returns `status: "denied"`. Kaji does not call the capability `execute` function.

A thrown or rejected authorization call also returns `denied`. The original error remains available as `result.error`.

## Ordering

Kaji validates input before authorization. Policy code always receives parsed input.

Kaji claims the idempotency key before authorization. This claim lets an identical retry observe the stored denial instead of running policy again.

Approval happens after authorization. An unauthorized request never reaches the approval handler.

## Policy ownership

Kaji enforces the authorization decision. Your application defines the policy.

Keep role checks, tenant checks, resource ownership, spending limits, and other business policy in application-owned code.

Kaji is not an IAM system. It does not issue identities, roles, sessions, or credentials.

## Example

```ts
const deleteProject = capability({
  name: "projects.delete",
  input: DeleteProjectInput,
  authorize: async ({ principalId, input }) => {
    return permissions.canDeleteProject(principalId, input.projectId);
  },
  execute: ({ projectId }) => projects.remove(projectId),
});
```

The adapter that calls Kaji must supply the correct principal:

```ts
await kaji.execute(deleteProject, {
  input: { projectId: "project_123" },
  principalId: session.userId,
  idempotencyKey: request.idempotencyKey,
});
```

Do not accept an untrusted `principalId` without application authentication.
