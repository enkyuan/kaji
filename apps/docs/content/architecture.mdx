title: Architecture
description: Understand Kaji's execution boundary, order, and ownership model.
---

Kaji runs inside your application. It governs the transition from a requested action to application code that can create a side effect.

```text
agent / automation / caller
            ↓
      application adapter
            ↓
      kaji.execute(...)
            ↓
   application capability
            ↓
 application / provider
```

## One execution path

`kaji.execute()` applies this order:

1. Validate the request and capability input.
2. Claim the execution identity in the configured store.
3. Check application authorization.
4. Request application approval when required.
5. Call the capability `execute` function.
6. Record the terminal result.

The claim step also decides two branch outcomes instead of continuing this order: an identical existing claim returns its stored or pending result, and a conflicting claim (same identity, different validated input) returns `status: "failed"`. Neither branch calls the capability.

The public API exposes no alternate execution path.

## The execution identity

Kaji combines three caller-visible values:

- capability name
- `principalId`
- `idempotencyKey`

The store also receives a fingerprint of the validated input. This fingerprint detects conflicting reuse of one idempotency key.

Kaji does not store the raw input through the `ExecutionStore` contract.

## Before capability execution

Validation, authorization, approval, and pre-execution cancellation happen before Kaji calls the capability.

A denied, rejected, or cancelled request prevents capability execution. Kaji records that result when the store remains available.

Claiming the idempotency key happens before authorization. This order makes retries of a denied or rejected request return the same stored result.

## After capability execution begins

After Kaji calls `execute`, an external side effect can start. A normal thrown error cannot prove whether that side effect committed.

Kaji returns `unknown` for this ambiguous case. Application code can use `knownFailure()` only when it knows that no side effect committed.

A timeout aborts the execution signal. It does not roll back a side effect or prove that a remote operation stopped.

## Store boundary

The `ExecutionStore` decides whether one claim is new, identical, or conflicting. It also records terminal results.

The store must coordinate concurrent claims for the same execution identity. Exactly one caller can receive `status: "claimed"` for that identity.

The configured store defines the persistence and coordination scope. `memoryStore()` coordinates only one process and loses all records at process exit.

## Ownership

Kaji owns the execution order, boundary enforcement, result classification, and minimal evidence.

The application owns identity, policy, approval systems, provider behavior, production storage, reconciliation, observability, and business audit data.

Kaji is not an IAM system, workflow engine, retry service, database, distributed lock service, event store, or recovery worker.
