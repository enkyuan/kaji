---
title: Troubleshooting
description: Diagnose capability, execution, approval, timeout, and store failures.
---

Start with the first error or result that you can reproduce. Then use the matching section.

## Capability construction fails

### `capability() requires a non-empty name.`

Give every capability a stable, non-empty name. Kaji checks the name when you create the capability.

### `capability() requires an authorize function.`

Define `authorize` for every capability. Kaji has no default authorization policy.

## `kaji.execute()` rejects before returning a result

Kaji can reject before it establishes an execution claim.

Common causes include:

- an empty `principalId`
- an empty `idempotencyKey`
- input parser failure
- `store.claim()` failure

Kaji does not call authorization, approval, or capability execution after one of these failures.

## A retry returns the previous result

An identical execution claim returns its pending or recorded result. Kaji does not call the capability again.

The execution identity contains:

- capability name
- `principalId`
- `idempotencyKey`

The validated input fingerprint must also match.

For a new operation under the same capability and principal, use a new idempotency key.

## A retry returns a `failed` conflict

Kaji returns a conflict when the same execution identity has a different validated input fingerprint.

```text
Idempotency key "..." was already used for a different request.
```

Use the original input for a retry. Use a new idempotency key for a new operation.

The same idempotency key can identify separate executions under a different capability or principal.

## The result is `denied`

`authorize` returned `false` or threw. Kaji did not call the capability.

Inspect the application authorization policy. Kaji does not explain or replace that policy.

## The result is `rejected`

The request required approval, but Kaji did not receive a valid approval.

Check these cases:

1. `createKaji()` has no `approve` handler.
2. The handler returned a value without `{ approved: boolean }`.
3. The handler returned `{ approved: false }`.
4. The handler threw or rejected.

All four cases prevent capability execution.

## The result is `failed`

`failed` is a definitive failure for the governed request.

Current cases include an idempotency conflict and an explicit `knownFailure(cause)` from capability execution.

The status does not state whether the error is retryable or permanent. The application owns that policy.

## Capability errors return `unknown`

Kaji treats a normal thrown or rejected `execute()` call as `unknown`. It cannot infer whether the side effect committed before the error surfaced.

Use `knownFailure(cause)` only when application code proves that no side effect committed.

```ts
execute: async (input, context) => {
  try {
    return await provider.refund(input, {
      idempotencyKey: context.idempotencyKey,
      signal: context.signal,
    });
  } catch (cause) {
    if (providerRejectedBeforeCommit(cause)) throw knownFailure(cause);
    throw cause;
  }
},
```

Kaji does not infer known failure from an error class, message, or status code.

## I want to retry `unknown`

Do not blindly retry. The original side effect can already have committed.

Use `result.evidence` and provider records to reconcile the operation.

Calling Kaji again with an identical claim returns the recorded `unknown`. It does not call the capability again.

Use a new idempotency key only after you prove that a new operation is safe.

## Cancellation did not stop the capability

Cancellation is cooperative. Kaji cannot forcibly terminate `execute()` or a remote request.

Pass `context.signal` to downstream APIs. Custom capability code must also observe the signal at safe points.

If `execute()` ignores the signal and later resolves, Kaji can return `succeeded`.

## `timeoutMs` elapsed, but Kaji still waited

This is the shipped behavior. `timeoutMs` aborts the effective `context.signal` after the configured duration.

Kaji continues awaiting `execute()` until it settles. Therefore, `timeoutMs` does not bound capability wall-clock time.

For the timeout to interrupt work, the capability or downstream API must observe the signal.

If `execute()` rejects after the abort, Kaji applies normal post-start ambiguity rules and returns `unknown`.

## The remote operation continued after an abort

An abort does not imply rollback. It does not prove that a remote system stopped or rejected the operation.

Reconcile the result with the downstream system before you create another operation.

## `store.claim()` fails

Kaji rejects with an error whose `name` is `KajiConfigurationError`. It could not establish the execution boundary.

Inspect store availability and the atomic claim implementation.

## `store.record()` fails

Kaji returns `status: "unknown"`. A side effect can already have committed, but Kaji could not confirm settlement.

Inspect the store before you retry or create a new operation.

## `memoryStore()` loses records

`memoryStore()` is process-local and non-durable. It loses all claims and outcomes when the process exits.

Use it for development, tests, and examples. Production deployments need an `ExecutionStore` with the required coordination and durability.
